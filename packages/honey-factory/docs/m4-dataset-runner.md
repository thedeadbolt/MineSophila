# M4: Dataset runner and levels 1–3

Recorded 2026-10-23 on the M0 reference setup: Minecraft 26.3, Fabric Loader 0.19.5,
Fabric API 0.163.0+26.3, OpenGL 4.6 core, Mesa 26.2.4, AMD Radeon RX 7600, Linux. The
design decisions are in
[ADR 0009](../../../docs/adr/0009-dataset-runner-and-levels-2-3.md).

## What exists

- `PlatformGenerator`, the shared base of levels 1–3, and two new generators:
  - `level2-clutter-v1`: scattered blocks and small piles, many yellow or orange, none
    touching the target.
  - `level3-partial-hiding-v1`: a wall, corner, recess or pillars against the target,
    plus background walls, pillars, stacks and scattered blocks.
- `SightLines`, a ray-cast estimate that discards hopeless viewpoints before any capture.
- Per-scene `generation.parameters`: the aim block, each viewpoint's accepted draw and
  the layout's counts and choices.
- Every pixel-affecting client option in `render_environment.settings`.
- `StorageBudget`: a disk preflight and the `output.free_space_reserve_bytes` reserve.
- Cancellation at operation boundaries, with documented semantics.
- Split-integrity and visibility-rule checks in the Java validator, which recomputes
  `scene-slots-v1`.
- `honey-factory-tools validate-dataset`, the independent outside validator.
- The shared mini dataset now has real PNG files.

## Exit gate

| Gate item | Evidence |
|---|---|
| Perspective smoke datasets for levels 1–3 reach their exact accepted-scene and target-balance quotas | Each level generated by command in a fresh world: 8 scenes (6 present, 2 absent) × 4 viewpoints at 640 × 480, `complete`. Every scene has the class and split `scene-slots-v1` assigns |
| They satisfy the visibility rules | Levels 1–2: all 24 positives `fully_visible`. Level 3: all 24 `partially_visible`, ratios 0.21–0.80 within the 0.2–0.8 rule. Both validators check every positive against the manifest's rule |
| They pass integrity and leakage checks | 0 errors from the Java `DatasetValidator` and 0 from `honey-factory-tools validate-dataset`. The outside validator checks schemas, single-record and cross-record rules, the slot plan (leakage), index digests and every image's bytes, hash, PNG format and mask statistics |
| Cancellation gives a valid terminal result or a diagnostic `failed` dataset, never a partial `complete` one | A 30-scene level-2 run cancelled by command after its first accepted scene: `failed` with failure `cancelled`, 4 scenes and 16 samples kept, the running attempt counted as failed and its images deleted. Both validators report 0 errors for what was kept. Unit tests cover cancelling during a reset, during a capture and after the final capture, which completes normally |

Every row passed in three `runClientGameTest` runs, each in fresh worlds. The last two
ran on the final code. Between them, all three levels reproduced `scenes.jsonl` (every
layout hash and generation parameter), all 32 masks and all 32 RGB images byte for byte.
`samples.jsonl` differed only in `capture.world_tick`, the game tick of each capture,
which depends on how long settling took. The game test is `M4DatasetTest`. It writes the
datasets and `summary.json` to `build/m4-datasets/`.

### Smoke datasets

| Level | Attempts | Scene rejections | Positives | Visibility ratios | Wall time |
|---|---:|---|---|---|---:|
| 1 | 8 | none | 24 `fully_visible` | 1.0 | 8.8 s |
| 2 | 8 | none | 24 `fully_visible` | 1.0 | 8.8–8.9 s |
| 3 | 8 | none | 24 `partially_visible` | 0.21–0.80 | 15.6–15.9 s |

With 8 scenes and the default 80/10/10 ratios, `scene-slots-v1` gives 7 train and
1 validation scene; test receives none. Small datasets cannot match the ratios, and
the manifest reports the actual counts.

Level 3 takes longer because some captures are re-drawn. The sight-line estimate keeps
only partially hidden views, but the saved mask must still fall within 0.2–0.8. In the
first run, its first 28 samples took 111 environment operations, against 36 for the first
16 of level 1 or 2.

## Generator behaviour

Measured over 40 scenes × 8 viewpoints with the default 50 draws per viewpoint
(`ClutterGeneratorsTest`):

| Level | Draws rejected before capture | Viewpoints with no placeable draw | Mean index of the first placeable draw |
|---|---|---:|---:|
| 2 | `camera_off_platform` 6,797; `target_occluded` 821; `camera_inside_block` 352 | 0 of 320 | 1.4 |
| 3 | `camera_off_platform` 5,701; `target_not_partially_hidden` 5,448; `camera_inside_block` 336 | 3 of 320 | 3.7 |

Off-platform draws dominate because targets near an edge put most azimuths outside the
arena. Level 3 rejects about half its placements as not partially hidden. Those draws
cost nothing: they never reach the game.

The images were reviewed by eye. Level-2 targets stand among piles of yellow concrete,
honeycomb, gold and other distractors. Level-3 targets peek out beside stone-brick walls,
corners and pillars. The masks cover exactly their visible parts. Target-absent scenes
show the same structures around an empty cell.

## Throughput

A level-1 or level-2 smoke dataset takes about 0.28 s per sample at 640 × 480,
including one reset per scene. The time is bound by ticks: every viewpoint change waits
at least 3 settling ticks (150 ms), and every reset at least 5.

PNG encoding a 1280 × 1280 capture takes about 32 ms for the RGB image and 9 ms for the
mask. That is under a third of the minimum settling time, so encoding stays on the
client thread. Moving it off would complicate the commit order for a modest gain;
revisit it if a production-size run shows otherwise.

## Still open

- **Production benchmark.** Disk use and samples per hour need measuring on a production
  run at 1280 × 1280 with 8 viewpoints before choosing the pilot's `accepted_scenes`.
- **Viewpoint-level rejections.** Draws and captures rejected inside an accepted scene
  are logged but not counted in the manifest, which counts rejected scene attempts only.
- **Level 4.** It needs a shape-aware sight-line estimate, because stairs, slabs, fences
  and foliage are not full cubes, or else it relies on capture-time filtering alone.
- **Interrupted runs.** A manifest left `generating` by a crash can only be regenerated,
  not resumed.
- Vulkan readback orientation is still untested (from M0).
